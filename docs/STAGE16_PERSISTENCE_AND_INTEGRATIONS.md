# Stage 16 — Persistence, API Reliability & Source Cache

**Status:** Complete within the local SQLite prototype boundary. This stage hardens storage/bootstrap and source download operations; it does not establish production identity, authorization, or consent verification.

## Reproducible setup

The database path is environment-configurable with `SKILLSCOPE_DATABASE_URL=sqlite:///./data/skillscope.db`. Relative paths are resolved from the project root, not the process working directory. `SKILLSCOPE_DATABASE_PATH` remains a compatibility fallback. In-memory and non-SQLite URLs are rejected because each repository opens independent connections and an in-memory URL would not provide reliable persistence in this MVP.

From the project root:

```bash
PYTHONPATH=backend python -m app.services.database init
PYTHONPATH=backend python -m app.services.database status
PYTHONPATH=backend python -m app.services.database init --db /tmp/skillscope-stage16.db --no-demo
```

The `init` command idempotently creates the legacy repository tables and applies checksum-tracked additive migrations. A changed SQL definition for an already-applied migration fails visibly instead of pretending a different schema was installed. SQLite connections enable foreign keys and a bounded busy timeout; the persistent database uses WAL mode.

`SKILLSCOPE_ENV=production` disables automatic demo seeding unless `SKILLSCOPE_SEED_DEMO=true` is explicitly set. `SKILLSCOPE_SEED_DEMO=false` disables it in every environment. `.env.example` contains dummy local values, never credentials.

## Durable data boundaries

| Data | Durable location |
|---|---|
| Student profile and typed evidence | `student_profiles`, `student_evidence_items` |
| Assessment questions/responses and submission status | `baseline_assessments`, `baseline_responses` |
| Challenge attempts and rubric-based evidence | `challenge_submissions`, evidence ledger in same transaction |
| Explicit journey/accessibility preferences | `student_preferences` |
| Career hypotheses generated by a specific policy | `recommendation_snapshots`, with algorithm version, evidence count, source keys and the serialized response |
| Saved pathway-plan snapshots and goal history | `pathway_plans` and dated evidence/goal records |
| Source acquisition freshness and cache/error state | ingestion run ledger plus `source_cache_state` when using the configured application database |
| Schema history | `schema_migrations` with SHA-256 of each migration definition |
| Synthetic showcase records | `demo_fixture_registry`, requiring `data_classification='synthetic_demo'` |

The synthetic profile is deterministic and seeded idempotently. Its goal, challenge submission, reflection and evidence are clearly labelled as synthetic. Re-running database initialization does not multiply demo profiles or challenge attempts. The fixture is demonstrative and must not be used to make decisions about a real student.

## Key Stage 16 APIs

- `GET /api/system/persistence` — non-sensitive persistence/schema and demo-fixture diagnostics; does not reveal the absolute SQLite path.
- `GET /api/student-profiles/{profile_id}/preferences` — load persisted preference state.
- `PUT /api/student-profiles/{profile_id}/preferences` — validate and persist journey preference, preferred domains, and accessibility format choices.
- `GET /api/recommendations/{profile_id}/history?limit=20` — list persisted recommendation snapshot metadata including algorithm version and referenced internal source keys.

The existing Stage 8–15 APIs continue to use the same database path. Recommendation snapshots are written only after lineage validation: every evidence reference must belong to the requested profile, and cited source references must resolve to `source_records` with an original record or publisher/source URI. A source record's existence does not assert that the source package was fully downloaded or that it has India-specific applicability.

## External-source download resilience

`download_asset()` only accepts predeclared allow-listed official asset IDs; it does not accept arbitrary caller-supplied URLs. The downloader enforces HTTPS host/port validation on every redirect, response timeout, bounded retry count, download-size ceiling, CSV header validation, SHA-256 checksum, and atomic `.part` → final-file replacement.

- **Cache freshness:** `SKILLSCOPE_SOURCE_CACHE_TTL_SECONDS` controls reuse; default is 86400 seconds and `0` disables cache reuse. A cache hit requires a matching source URL/version, parseable timezone-aware retrieval time, valid header, and matching file checksum.
- **Rate limiting/retries:** source attempts have a minimum interval and retryable 429/5xx/network/timeout errors use bounded backoff. Numeric or HTTP-date `Retry-After` is honored up to a bounded three-second wait; requests asking for a longer wait fail rather than retrying immediately against the source.
- **Stale file behavior:** a cache past TTL triggers refresh. A failed refresh never replaces the previous file or metadata sidecar; the run ledger records `download_failed`, preserves the last successful operation, and cache state records `refresh_failed` when the old file exists. Callers must not treat that preserved file as fresh merely because it remains on disk.
- **Failure isolation:** source acquisition is not a prerequisite for creating or reviewing a profile, completing a challenge, or reading existing student evidence. Graph-dependent career recommendations deliberately report the unavailable/stale catalog instead of fabricating occupational facts.
- **Status:** cache/run metadata describes a pinned static snapshot (`source_data_is_live=false`), not a live feed. The full O*NET Database and ESCO package are still not integrated in this environment.

The downloader writes the existing JSON ingestion run ledger for all download outcomes. When using the default configured application state path and a migrated database, cache status is also best-effort-updated in `source_cache_state`. Failure of this supplementary cache telemetry does not block an otherwise valid source operation.

## Safe API errors and operational identifiers

Each HTTP response gets a fresh server-generated `X-Request-ID`. SQLite failures return a generic 503; unhandled failures return a generic 500 with the request reference. Raw exception messages, database paths and internal diagnostics are retained in server logs, not exposed in the API response. `/api/system/persistence` gives only non-sensitive readiness information.

## Limitations and production blockers

- The API remains unauthenticated and there is no server-side profile ownership check. Profile UUIDs are not credentials.
- Consent is recorded as a self-attestation; guardian identity/authority is not independently verified.
- The configured store is local SQLite, not a managed multi-instance production database.
- No full-data O*NET/ESCO import occurred here. Source licenses and record-level terms still govern external reuse.
- Full frontend TypeScript typecheck and Vite production build remain unverified where npm dependencies cannot be installed.
- Backups, retention enforcement, export operations, deployment TLS/secrets management, abuse protection, and a security/privacy audit remain before external deployment with real student/minor data.
